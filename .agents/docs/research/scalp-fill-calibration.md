# 指値の約定率の答え合わせ（計画 Q2 / 最初の作業 1）— 2026-11-08

計画: `rl-scalp-limit-plan.md`。スクリプト: `scripts/probes/fill_calib.py`（仮想注文の生成と判定）、`fill_calib_report.py`（集計）、`fill_rule_fit.py`（歩み値だけで動く中間ルールの学習と検証）。出力: `.cache/trading_rl/fillcal/orders.npz`（149万件）。

## データ
- 板 `S:/jp/stocks_board_kabu_push`（10段・約50銘柄）と、歩み値 `S:/jp/stocks_trades`（J-Quants、約定1件ずつ）が重なる日のうち、**使えたのは9日**: 07-09, 07-13, 07-14, 07-17, 07-21, 07-22, 08-12, 08-13, 08-14。
  - 除外した日: 07-10（板の累計出来高が歩み値と一度も一致しない）、07-16（記録は 15:08 以降のみ）、07-23（空）、08-11（24行のみ）、08-28（歩み値なし）。
- 時計合わせ: 板の時刻（記録PCの時計）と取引所の時刻は、日によって −0.9〜+1.2 秒ずれる。累計出来高が一致する時点を探して日ごとに補正する。板1行と約定の対応は、時刻ではなく累計出来高で取る（その行の時点で約定が何件含まれているか）。
- 古い板の除外: 2秒より前の約定を含んでいない板の行や、30秒以上前の行は使わない（記録の開始が遅れた日がある）。

## 方法
前場の 09:00:30〜11:29 に20秒おきに、各銘柄の買い・売りそれぞれで100株の仮想指値を置き、注文の寿命は60秒とする。注文は判断から200ミリ秒後に有効になる。指値の値段は4種類:
- join: 最良気配
- last_k0 / k1 / k2: 直近値から 0 / 1 / 2 tick 有利な側（今の ScalpEnv の行動と同じ形）

同じ注文を4通りの決め方で判定する:
- touch: 指値と同じ値段で約定が出たら約定
- trade_through: 指値を越える値段で約定が出たら約定
- queue_fifo: 有効になった時点で板に出ている同じ値段の数量を「前に並ぶ量」とし、その値段の約定がそれを100株上回ったら約定。取消は考えない
- **queue_cap（主な推定）**: queue_fifo に加え、前に並ぶ量は「いま板に出ている数量」を超えないとする（板の数量が減ったら、前の注文が取り消されたとみなす）

置いた時点で反対側の気配に届いている指値（marketable）は、その場で反対側の気配の値段で約定とする。

約定後の動きは、約定の 1/5/10/30 秒後の仲値と約定値の差（tick、有利なら＋）で測る。

## 結果1: 4通りの判定の比較（9日・最良気配に並んだ指値・すぐには約定しなかったもの）
| 判定 | 10秒以内の約定率 | 60秒以内の約定率 | 約定1秒後の動き | 約定30秒後の動き |
|---|---|---|---|---|
| touch | 60% | 83% | −0.15 | −0.34 |
| trade_through | 36% | 67% | −1.15 | −1.41 |
| queue_fifo | 43% | 73% | −0.74 | −0.96 |
| **queue_cap** | **47%** | **76%** | **−0.58** | **−0.79** |

- 本物（の推定）は touch と trade_through のほぼ中間にある。trade_through（前回の主ルール）は、約定の不利さを約0.6 tick 厳しく見ていた。
- それでも、何も考えずに並ぶと、約定した時点で −0.6 tick 前後不利になる（不利なときにだけ刺さる「逆選択」）。スプレッド1 tick のときは −0.34、2 tick 以上のときは −0.77。時間帯別では、寄り後10分が最も悪く（−0.83）、10時以降が最も良い（−0.52）。
- 直近値ちょうど（last_k0）の指値は、34% がその場で約定する（成行と同じになる）。k1 では 4.9%、k2 では 1.5%。

## 結果2: 歩み値だけで動く中間ルール（ScalpEnv に入れる候補）
- ルールの中身:
  - ① その場で約定する確率を分類器で推定する（HGB・AUC 0.89）
  - ② 前に並ぶ量を回帰で推定する（HGB・対数での相関 0.71）
  - その量の仮想の列に並ばせ、指値の値段の約定がそれを100株上回るか、指値を越える約定が出たら約定とする
  - 縮小係数 c は 1.0（縮めない）
- 特徴（すべて判断時点までの歩み値だけから作る）: k、売り買いの向き、直近1/5/30秒の値動き、直前の値動きの向き、5秒高安の中での位置、10秒の約定件数、10秒の出来高（1回あたりの株数との比）、1回あたりの株数の中央値、呼値の大きさ（価格比）、値動きの細かさ、時刻。
- 学習は前半5日、**検証は後半4日**:

| 判定 | 10秒以内の約定率 | 60秒以内の約定率 | 約定5秒後の動き |
|---|---|---|---|
| touch | 54% | 78% | −0.42 |
| **中間ルール** | **49%** | **73%** | **−0.80** |
| queue_cap | 47% | 72% | −0.73 |
| trade_through | 40% | 66% | −1.18 |

- k 別・時間帯別でも、約定率の差は ±3 ポイント以内、約定後の動きの差は 0.04〜0.16 tick で、中間ルールが少し厳しい側に出る。安全側の誤差なので、これを主な判定に使える。

## 注文が届くまでの時間（2026-07-13 のライブ記録 `S:/jp/orderbook_churn_live`）
- 新規注文の HTTP 往復は **150〜190 ms**（今の ScalpEnv は 50 ms）。
- 注文を連続して出すと、2件目以降は1件ごとに約1秒待たされている（プローブ側の間隔制御か、kabu 側の制限かは記録からは判別できない）。
- ライブの約定（14件中6件）と判定との突き合わせはできなかった。ライブ側が見ていた板と記録の板の行が一致せず、寄り付き直後は記録が抜けており、件数も少ない。

## 限界
- queue_cap も推定にすぎない。前に並ぶ注文の取消は、板の数量が減ったときしか分からない。判定は本物より少し厳しい側に出ていると考えられる。
- 9日・約50銘柄のみ（2026年7〜8月）。2024〜2025年の学習期間に同じ関係が成り立つという前提を置いている。
- 約定後の動きは仲値基準。手仕舞い（指値か成行か）の損益は含まない。

## kabu 配信の粗さ（AIに見せる特徴用）
- kabu の配信で、出来高が変わった1回あたりに含まれる約定は 1.26〜1.58 件だった（2026-08-13、8銘柄）。配信の間隔の中央値は 80〜1840 ms で、銘柄によって大きく違う。
- 「最初の約定から 20 ms 以内の約定をひとまとめにする」と、8銘柄すべてでこの比率をほぼ再現できた（1.26〜1.60）。50 ms 以上でまとめると、粗くしすぎになる。
- → `ScalpConfig.obs_tape="push20"` / `build_scalp_session(obs_tape="push20")` を追加した。AIに見せる特徴だけをこのまとめた歩み値から作り、約定の判定には約定1件ずつのデータを使う。
