## Implementation Plan: Browser-side Pyodide Replay Strategies

Status: planning only; no application implementation is included in this document. CodeMirror 6 was approved for the first user-facing strategy editor on 2026-09-10.

### Purpose

Enable a user to author a Python strategy in an embedded CodeMirror 6 editor, run it in the browser during TickReplay, receive host-provided market and account state only after it has occurred, and submit simulated order intents through the existing paper-trading rules. The design must keep the UI responsive, make successful in-budget callbacks independent of replay speed and Worker timing, preserve the existing manual-order behavior, and prevent stale or malformed Python results from mutating replay state. Because same-origin browser Python can call Web APIs itself, “host-provided past-only snapshots” is an API contract, not a technical guarantee that trusted user code cannot fetch other data.

The recommended architecture is a pinned Pyodide runtime inside one module Web Worker, controlled by a small main-thread state machine. The browser's existing JavaScript replay and paper-trading engine remains authoritative for time, orders, fills, position, and P&L. Python receives immutable snapshots and returns declarative commands; it never receives a DOM reference, the complete future replay dataset, or a callable that directly changes trading state.

#### Research conclusion

Pyodide is feasible for this feature. Its official documentation recommends a Web Worker when Python work must not block the UI, and the current stable Worker example requires a module-type Worker.^1 Pyodide's JavaScript API provides the required code execution, custom globals, stream redirection, package loading, and interrupt hooks.^2 The critical limitation is that browser Python has access to Web APIs, so a Worker is an execution and responsiveness boundary, not a security sandbox.^3

The adjacent marimo project validates the broad shape: a module Worker owns a long-lived Pyodide runtime, a singleton bridge exposes typed RPC, runtime state is explicit, Python/JavaScript calls cross a fixed bridge, and `SharedArrayBuffer` is used for cooperative interrupt when cross-origin isolation is available. The reusable subset is the Worker, state machine, fixed protocol, bounded streams, version pinning, and interrupt design. Its notebook graph, cell protocol, completion engine, filesystem UI, package UI, and general kernel are deliberately excluded.

CodeMirror 6 is the selected normal editor rather than Monaco or a native textarea as the normal editing experience. CodeMirror is modular, distributed as ES modules, and supports a Python language package plus pluggable diagnostics.^13 ^14 ^15 Version 1 uses it as a single-file code editor, not as a Python IDE: semantic type analysis, runtime introspection, and a language server remain separate concerns. A native textarea remains permanently in the HTML as a hidden progressive-enhancement/recovery surface, not as a competing primary editor.

#### Proposed runtime flow

```text
Replay tick i
    |
    v
Main thread applies tick i
    |
    v
Match orders eligible at i; commit fills and portfolio
    |
    v
Create immutable post-tick snapshot (no future data)
    |
    v
StrategyController --typed message--> Pyodide module Worker
    |                                      |
    |                                      v
    |                               Python on_event(event)
    |                                      |
    |<-- validated plain order commands ---|
    |
    v
Stage commands atomically with eligible_from_session_tick = i + 1
    |
    v
Replay tick i + 1
```

This ordering is a design recommendation derived from the current replay loop. Today, `src/tickreplay/static/app.js` applies all ticks in a rendered frame before `matchOrders()` evaluates existing limit orders. If an asynchronous Python response were simply added at the end of that frame, its orders could be incorrectly matched against ticks that occurred before the strategy produced them. A per-tick strategy barrier prevents that look-ahead by construction.

### Scope

The scope keeps Python execution entirely in the browser and limits version 1 to the smallest deterministic strategy surface that reuses the existing simulated broker.

This plan uses two distinct recovery terms in UI copy, test names, and documentation. **Degraded strategy editor** means the workspace host is healthy but CodeMirror is unavailable: the synchronized textarea retains every strategy source action and execution control. **Raw copy recovery** means the workspace host itself failed: only the HTML-native source text can be selected/copied, strategy actions are unavailable, and ordinary replay/manual trading continues. The generic word “fallback” must not blur these different guarantees.

#### In scope

- A single user-authored strategy and a single Pyodide Worker at a time.
- Code authored by the current user. Execution of third-party or shared untrusted strategies requires a separate security design.
- A small, versioned Python ABI: `on_start`, `on_event`, and `on_end`.
- Tick events containing the current absolute session tick index, fills produced at that tick, a run-local monotonic fill-delivery cursor, and the resulting account snapshot.
- Simulated market orders, simulated limit orders, and cancellation commands supported by the existing paper broker.
- Deterministic single-flight processing for callbacks that complete within the configured deadline: at most one unresolved strategy callback, with explicit backpressure. Timeout is an environment-dependent terminal run failure and is recorded as such.
- Worker startup, code loading, start, pause, stop, timeout, hard restart, seek/reset invalidation, session change, source revision, and replay-end semantics.
- Bounded stdout, stderr, error, payload, queue, and intent handling.
- A single-file CodeMirror 6 editor with Python highlighting, line numbers, indentation and bracket support, search, undo/redo, version-tagged diagnostics, and ABI-scoped static completion.
- Explicit Save Draft, Load, Start, Stop, Restart, `.py` import/export, sample insertion, and visible draft/saved/loaded/running revision state.
- Versioned browser persistence for source and editor settings only; saved code is never auto-executed.
- Pinned, self-hosted Pyodide runtime assets and an allowlisted package set.
- CSP, COOP/COEP, MIME, caching, local FastAPI, and Cloud Run delivery behavior.
- DOM-independent unit tests, Python wrapper tests, FastAPI response tests, and real-browser acceptance tests.

#### Out of scope

- Evaluating user Python on the FastAPI or Cloud Run backend.
- Live brokerage, external order routing, or access to secrets.
- Multiple concurrent strategies or multi-account simulation.
- Arbitrary `micropip.install()`, automatic imports that download packages, direct network access as part of the reproducibility contract, or a package manager UI. Same-origin trusted code is not technically prevented from using all Web APIs in version 1.
- Notebook cells, reactive execution, multi-file editing, formatting, a file tree, a virtual filesystem UI, general Python semantic completion, Pyright/LSP integration, debugging, or code navigation.
- Monaco Editor. Reconsider it only if multi-file models, code navigation, or language-server-backed IDE behavior becomes a product requirement.^16
- Persisting or restoring the Python heap, Worker memory, or Pyodide filesystem.
- Treating import restrictions, AST inspection, custom `jsglobals`, or a same-origin Worker as a hardened sandbox.
- Maintaining x500 wall-clock speed when the Python callback cannot keep up. Correct event ordering takes precedence.

#### Strategy ABI v1 proposal

The Python source defines either functions or a `Strategy` object normalized by `strategy-runner.py` to this logical interface:

```python
def on_start(context: dict) -> None:
    """Initialize strategy-local state; version 1 cannot return commands."""

def on_event(event: dict) -> list[dict] | None:
    """Observe one committed event and return zero or more order commands."""

def on_end(summary: dict) -> None:
    """Receive a final read-only summary; returned orders are ignored."""
```

`on_event` v1 receives one `tick` event at a time:

```text
protocol_version
session = {stem, code, actual_date}
run_id
strategy_revision
sequence                      # RPC sequence, not tick identity
tick = {session_tick_index, replay_time_us, price, quantity, trade_type}
fills = [...]                 # fills committed while processing this tick
fill_cursor                   # last run-local fill_delivery_sequence; starts at 0
portfolio = {...}             # post-fill snapshot
open_orders = [...]           # bounded, strategy-visible representation
```

The exact field names are frozen in Step 3, but the following invariants are mandatory:

- No field exposes a future tick, the all-day typed arrays, mutable JavaScript state, DOM objects, or callbacks.
- Time uses replay time, not `Date.now()` or Worker wall time.
- Session identity, run ID, revision, RPC sequence, and absolute `session_tick_index` appear in every tick request and response envelope. Ticks sharing a timestamp remain distinct. A new run after seek gets a new run ID but retains the immutable session-array tick index.
- Data crossing the Worker boundary is structured-cloneable plain data. Worker messages use the browser structured clone algorithm.^7
- Prices must be validated against the existing tick grid and use the one canonical Step 0 representation—integer logical levels or decimal strings—through spike fixtures, ABI, trace output, and implementation; unconstrained binary floats are not the protocol authority.
- Python output is deeply converted to plain JavaScript with `create_pyproxies: false`, and every retained `PyProxy` is destroyed in `finally`. Pyodide explicitly requires proxy destruction to avoid leaks.^8

Order commands are a discriminated union, initially limited to:

```text
submit_market          {client_intent_id, side, quantity}
submit_limit           {client_intent_id, side, quantity, limit_price_or_level}
cancel_strategy_orders {client_intent_id, optional_side}
```

The main thread validates the complete returned list before making any mutation. Unknown keys or versions, duplicate client IDs, unsupported command types, non-finite or out-of-range values, wrong instruments, stale envelopes, and limit violations reject the entire batch. At the boundary before the next unseen tick, valid cancellations are applied first and submissions second in returned-list order, as one transaction. Strategy cancellation is restricted to open orders owned by the current session/run/revision and optional side; an already-absent target set is an idempotent no-op. Manual cancellation retains its existing side-wide behavior. The main thread assigns canonical order and internal fill IDs and timestamps. Separately, each strategy run assigns contiguous `fill_delivery_sequence` values starting at 1 only to fills delivered to that run. Python cannot submit fills or set cash, position, average price, realized P&L, or replay time.

For each tick, the normative broker order is: apply eligible strategy cancellations; register eligible strategy market/limit submissions and assign canonical order IDs in returned-list order; apply the market tick; evaluate every eligible market/limit order in ascending canonical order ID; append fills and marker events in that same order; then publish the post-fill event snapshot. This makes pre-existing orders run before newer strategy orders without inventing exchange priority. Manual limit aggregation remains exactly side-and-level aggregation among manual orders. Strategy limits remain separate per canonical order and are never aggregated with manual orders or another strategy command, preserving run ownership and cancellation scope.

For an event whose absolute session tick index is `i`, every returned submit or cancel has `eligible_from_session_tick = i + 1`. It becomes effective after tick `i` has fully matched and before tick `i + 1` is applied. If `i` is the final session tick, the batch is validated and reported for diagnostics but cannot be committed because no eligible tick exists.

`on_start(context)` receives session/run/revision identity, `next_session_tick_index`, nullable `last_committed_session_tick_index`, nullable `last_replay_time_us`, nullable `last_price`, the authoritative portfolio, and bounded open orders. At cursor 0, `next_session_tick_index` is `0` and all three last-committed market fields are `null`; no price, time, quantity, trade type, or other value from tick 0 is exposed until `on_event` delivers it. At a later cursor, the last-committed fields describe exactly `next_session_tick_index - 1`. An empty/exhausted session has no valid Start transition.

#### Lifecycle semantics proposed for v1

| Action | Strategy behavior | Order/result behavior |
|---|---|---|
| Load source | Invalidate any run and terminate its Worker, compile the selected canonical draft in a fresh candidate Worker, and allocate a new loaded revision only after compile and ABI validation succeed | Old responses and staged commands become stale; a failed candidate is terminated, Start remains disabled, and the prior immutable loaded source/revision remains available only for explicit Restart |
| Start | Allowed only while replay is paused with at least one unseen tick; cursor 0 is valid with nullable last-committed fields. In one synchronous main-thread transition, capture session generation/identity, cursor as next unseen tick, nullable last-committed tick/time/price, portfolio, open orders, and Play/Pause state; create run ID/sequence; enter `starting`; disable Play/manual entry; then call non-ordering `on_start` | No event dispatch while `starting`; success enters strategy `paused` while replay stays paused; no historical event replay and no `on_start` commands; tick 0 data is not exposed early, and the first possible command comes from the first subsequently processed `on_event(i)` and is eligible at `i + 1` |
| Replay pause | Stop dispatching new events; keep Worker and strategy state | An in-flight valid result may finish and be staged while paused if all identities match; Resume commits it before the next unseen tick |
| Replay resume | Continue with the next unseen tick | Existing eligible orders remain active |
| Stop strategy | Invalidate run, attempt cooperative interrupt, then terminate if needed | Discard staged commands and cancel current-run strategy orders; manual controls become available again |
| Callback timeout or terminal strategy/Worker/protocol error | Invalidate the result, cancel current-run strategy orders, and transition the run to error with replay paused | Do not silently skip the event, keep strategy orders alive, or resume replay; explicit Stop/Restart or manual replay Resume is required |
| Hard restart | Terminate the Worker and rebuild only from the last successfully loaded immutable source/revision | Python state is lost; the current draft and saved draft are not promoted implicitly; no automatic restart of trading |
| Seek | Invalidate and stop the strategy run before `seekTo()` completes | Discard queue/staged commands; never apply a pre-seek response |
| Reset | Stop strategy and reset simulated trading per current behavior | Source may remain, but is not automatically executed |
| Session change | Terminate the Worker before committing the new full session identity | Reject all old session responses and commands |
| Draft edit/autosave | Increment `draft_revision` only for a source-changing editor transaction/import/sample/conflict resolution; saving copies that exact revision into a new storage record and reports only point-in-time read-back confirmation | Running/loaded Worker and loaded/running revisions remain unchanged; a later cross-tab overwrite transitions the draft to `superseded` |
| Explicit Load | Invalidate any old run, terminate its Worker, canonicalize and compile the selected draft in a fresh candidate Worker, and assign a new loaded revision only on success | Old executable responses become stale; failed load preserves the candidate draft and the prior loaded source/revision metadata but leaves no active Worker and disables Start until explicit Restart or another successful Load |
| Replay end | Allow the last admitted callback to finish only within its normal deadline for logs, ignore its commands because no eligible tick exists, cancel remaining current-run strategy orders with one `replay_end` diagnostic, then call non-ordering `on_end` once under its shorter best-effort deadline | No command may invent a post-session fill; `on_end` timeout/error adds a diagnostic but does not run terminal cleanup twice or delay Worker termination; manual orders retain existing end behavior |
| Page unload | Flush a non-conflicting dirty draft synchronously through the verified storage path on `visibilitychange`/`pagehide`, warn with `beforeunload` while a dirty or conflicted draft remains, then perform best-effort strategy cleanup and Worker termination | Browser lifecycle delivery is not guaranteed, especially on mobile; the normal 750 ms autosave and explicit Save/Export are the primary protection; no persistence except versioned source/settings |
| Background / BFCache | On `visibilitychange` to hidden, stop new dispatch, pause replay, flush the draft, and preserve only an identity-checked in-flight result; on visible, reset the replay scheduler's wall-clock anchor and remain paused until explicit Resume. On `pagehide`, synchronously invalidate the run, discard staged commands, cancel its strategy orders, mark execution suspended, and terminate the Worker. | A `pageshow` with `persisted=true` reasserts paused replay, clears timing debt and stale execution UI, renders the authoritative broker state, and requires explicit Restart from the last loaded source; draft/source recovery remains available and no wall-clock catch-up occurs |

The initial implementation should not attempt automatic strategy-state reconstruction on seek. Starting after a seek creates a fresh run at the selected cursor and receives the current authoritative account snapshot. Deterministic replay-from-start reconstruction or checkpoints are possible later features and require a separate design.

Version 1 deliberately prevents new manual submits and cancels while an automated strategy run is active or has an unresolved callback. This avoids a wall-clock-dependent ordering race between a user click and a Worker result. Manual orders already open when the strategy starts remain authoritative, may fill normally, are visible with their source in bounded snapshots, and cannot be canceled by Python. A later mixed manual/automated mode would need to record manual actions in the deterministic event log and define a linearization point; it is not implicit in this plan.

### Implementation Steps

The steps are ordered to resolve browser feasibility and trading semantics before building runtime, UI, and deployment layers. | Risk | Impact | Mitigation / gate |
|---|---|---|
| Per-tick Worker round trips cannot sustain requested replay speed | x100/x500 playback becomes slower than wall-clock target | Measure first; use single-flight correctness in v1; retain batched DOM painting; do not batch strategy decisions until equivalent fill-feedback semantics are proven |
| Async response creates look-ahead or retroactive fills | Invalid backtest results | Per-tick commit barrier; absolute `eligible_from_session_tick`; golden traces across callback delays and replay speeds |
| Existing manual order semantics regress during broker extraction | User-visible trading behavior changes | Characterization tests before extraction; retain existing fill/P&L functions; compare canonical traces |
| Timeout rejects a promise but Python continues running | CPU remains consumed and later result may arrive; slower devices may terminate a run that succeeds elsewhere | Invalidate identity first; record deadline/capability/performance class; classify timeout as an explicit terminal operational failure; cooperative interrupt when available; terminate and recreate Worker as the hard guarantee |
| Stale result crosses seek, session, or source revision | Order is inserted into the wrong replay state | Validate full session identity, run ID, revision, and sequence immediately before atomic commit |
| Partial acceptance of a malformed command list | Strategy state and broker state diverge | Validate the entire list first; commit all or none; return a structured rejection event |
| PyProxy lifecycle leaks Wasm/Python memory | Long sessions degrade or crash | Worker-only ownership; `create_pyproxies: false`; `finally` destruction; long-run memory tests |

| Worker is mistaken for a security sandbox or “past-only” data guarantee | User or future shared code accesses same-origin capabilities or fetches other data | Describe snapshots as host-provided inputs only; trusted-current-user scope; minimal capabilities; CSP; no privileged callbacks; separate-origin threat model before shared code |

#### Security boundary

Pyodide and a dedicated Worker protect main-thread responsiveness and reduce accidental coupling, but do not create an adversarial-code sandbox. Pyodide states that browser Python has full Web API access.^3 A same-origin Worker can therefore reach browser networking and storage capabilities available to its context. Restricting `jsglobals` is useful defense in depth, not a reliable authority boundary.

Version 1 must be labeled for code trusted by the current user. If importing, publishing, sharing, or executing third-party strategies becomes a requirement, implementation stops at a separate security decision gate. That design must consider an isolated origin without application cookies or secrets, a narrow cross-origin message contract, network/storage policy, resource-exhaustion controls, and an explicit threat model. AST or import blacklists are not an acceptable substitute.

#### Performance and determinism

Pyodide startup and Python execution are materially more expensive than ordinary in-page JavaScript, and the official documentation warns that main-thread WebAssembly can make the UI unresponsive.^12 The Worker resolves UI responsiveness, not throughput. The main performance risk is one message round trip and Python callback per tick, particularly for sessions with roughly 100,000 executions.

CodeMirror stays on the main thread, so bundle parsing, initialization, diagnostics, and document updates need separate UI budgets. If Step 1C measurements require it, load the committed editor bundle only when the strategy workspace first opens; lazy loading must not change draft recovery, asset-failure behavior, CSP, or offline behavior.

The initial contract therefore makes a deliberate trade: preserve causal order and slow the effective replay clock when the strategy is behind. It does not drop events, run callbacks concurrently, or continue the virtual clock while a result that should affect the next tick is unresolved. Future optimization may use shared memory or safe batching only after proving identical order/fill/portfolio traces, including fill feedback between decisions.

For repeatability, the run record should capture dataset/session identity, strategy source hash, protocol version, Pyodide/Python version, approved package lock hash, user configuration, and optional random seeds. Strategy code must use replay timestamps. Network-derived data, wall-clock time, locale-dependent parsing, and persistent Python filesystem state are outside the reproducible contract.
